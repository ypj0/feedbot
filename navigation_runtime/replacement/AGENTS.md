# 故障记录与回归要求

用户明确要求：每次故障必须记录原因并加入测试，禁止仅针对某次现场表现打补丁。

- 先保存原始日志、输入、版本与运行配置；后重启、清理或部署。证据包含令牌/密码时不得写入报告。
- 在 `incidents/ledger.json` 为每个独立失效模式建立条目，记录触发条件、证据、确定原因与未知部分、修复、测试和实车验证状态。不得把症状或推测标成确定根因。
- 每项行为修复必须添加或扩展能覆盖该失效机制的回归测试，包含正常情况和必要的拒绝/停车反例。可重用已有测试，但要指出具体覆盖项及未覆盖部分。
- 有价值的现场输入放入 `native_ros/testdata/`；测试不得依赖临时目录或车机上偶然留下的文件。
- 用 `native_ros/run_regressions.py` 统一运行对应层级，报告测试结果及源码 SHA256。分开报告“测试通过”“已部署”“静态实车就绪”“实车运动验证”，不得混用。
- 故障复现和负载测试默认在无设备的隔离容器中进行。不得为了验证自动发起实车运动，不能自动恢复旧任务。
- 缺少故障瞬间证据时保留 open/needs_evidence 状态；后续一次成功不能关闭该故障。
- 修复属于所有相关输入和生命周期的共同机制，不能按某条路线、某个坐标或某次目标编写例外。

## 全面修复原则（用户持续要求，2026-11-08）

- 用户明确要求每次全面处理，禁止只针对局部症状打补丁。后续各轮均遵循，不需用户重复提醒。
- 修复前写明根因证据、尚未证实的解释、受影响链路和相邻模块的状态/时序契约；不得把新增兜底等同于底层原因已消除。
- 验收必须覆盖故障输入到最终执行授权的跨模块流程，以及恢复、取消、断联、旧结果迟到和地图/坐标版本变化等适用边界。
- 单个案例通过、模块单测通过或静态就绪不能证明整体稳定。报告需区分机制修复、隔离端到端验证和真实运动验证，保留尚未解决的精度/性能问题。
- 参考原厂时注明部署源文件、反编译证据与上游参考实现的区别；不得把上游行为未经核实当成原厂完整逻辑。
