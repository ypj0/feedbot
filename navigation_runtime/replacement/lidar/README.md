# LT-R2 原始网络数据 → ROS2 扫描：第一阶段

本目录是直接读取雷达网络数据的候选实现，当前完成被动抓包、独立解析及断网ROS2回放。
不是已经替换原厂的常驻雷达驱动。没有启动/停止雷达、修改配置、升级固件或停原厂节点。

## 已核实的硬件与格式

- 实机 enp2s0：192.168.10.200 → LT-R2 192.168.10.160。
- 原厂PID1487持有TCP2105控制连接；数据另走UDP2105，不能把TCP控制口当作全部扫描数据。
- 原始报文被动抓取5.02秒：607个UDP包及1个TCP包，文件SHA256：
  6488014069242d59880aada10b3d45a5af2ec296178f84ace472705d472dbcbc。
- UDP每包1040字节：16字节头，256个16位距离与256个16位强度。
- flags=0x0101，即360°、16位强度；每圈8块，共2048束。距离按厂商SDK定义为2mm单位。
- 按原厂参数±1.65rad裁剪得1075束；离散采样实际首末角为±1.647495rad。
  新消息报告实际采样角，使angle_max=angle_min+(N-1)*angle_increment。
- 型号/网络/裁剪参数从实机核查；距离比例与方向依据厂商源码，仍需实景距离/方向对照。

## 结构

packet.hpp：以太网IPv4/UDP边界 → OOB完整长度/CRC → 连续块重组 → 扫描几何。
拒绝分片IP、不支持的格式、损坏CRC、长度不匹配、缺失/重复/混帧数据。
只发布完整帧，下一帧0号块恢复组装，不以零距离填补缺块。
当前明确只支持已观测LT-R2的360°格式；没有声称支持所有LTME型号和协议。

replay.cpp：与ROS无关的C++解析验证。node.cpp：同一解析器输出标准ROS2 LaserScan，
仅发布/candidate/scan，保留抓包时刻，不把旧录制数据冒充实时数据。
节点没有ROS1订阅，未连接/Nav2或底盘执行接口。

时间估计暂采用首块主机接收时刻与设备块时间差推算首束时刻，并加裁剪偏移。
本次设备timestamp差值符合微秒计数，但绝对时间同步与块时间代表起点/终点尚待实测；
不能将这一估计用于未经验证的运动去畸变。上游ROS1节点同样采用接收时刻估计，
不能仅因原厂这样实现就视为已校准。

## 控制面与生命周期核心（模拟验证完成，未接管实机）

lifecycle.hpp定义单一控制线程的状态机：Disconnected → Inactive → Starting → Active，
以及Sleeping、Fault。启动成功应答不等于Active；必须在1秒启动窗内收到属于当前epoch、
产生于本次激活之后且不超过200ms年龄的完整扫描。Active超过300ms无帧进入Fault。
这些是候选健康监控参数，不是电机停止距离保证。

stop首先撤销ready，再分别尝试stopStreaming、stopMeasurement；任一步失败保留Fault，
不能声称硬件已经休眠。退出与所有权丢失清空就绪状态。重连只configure回Inactive，
不自动恢复测量；上层必须重新明确activate。此为普通C++核心，尚未接入ROS2 LifecycleNode。

sdk_control.hpp复用固定版本厂商SDK，控制连接只调用DeviceBase::open，避免Device::open
隐式绑定UDP端口。configure只查询型号、OOB状态、目标地址及端口，不写持久化配置。
没有重启、刷固件、改频率、改过滤参数。原生数据解析不使用SDK内缺少完整包长检查的路径。
厂商旧依赖在GCC13有警告，保留构建日志；不能把编译成功当作控制协议已全面抗畸形输入。

lifecycle_test.cpp覆盖缺失所有权、各阶段失败、陈旧/重复/旧epoch数据、超时、休眠/唤醒、
停止部分失败和重新配置不自启动；本机ASan/UBSan通过。
sdk_fixture.py在127.0.0.1模拟雷达，验证SDK真正发出的TCP封装、CRC和14步调用顺序。
模拟器并未实现真实测量，fixture中的就绪帧是显式注入，不声称硬件收到了命令。
上述测试在内部车机断网Jazzy容器构建运行通过；无真实雷达连接、测试结束无残留容器。
重现：stage_sdk.py上传固定源码，deploy_sources.py上传候选，
车机bash /opt/feedbot-nav2/lidar/run_control_fixture.sh。

### 实机交接前必须完成的所有权整合

实机原厂雷达PID1487，父进程为管理程序PID1296，绑定0.0.0.0:2105 UDP。
已核对在用mapserver_manager.py的SHA256与本地恢复文件一致：
1a00b171baa1f75d8fc68296f3ca08f94afe7c68e45931616edd6fdafbf65884。
该文件1383行附近：scan_status达到20、已初始化且startScan启用时，会shutdown_scan后
loading_scan。不能将“kill原厂雷达进程/端口短暂空闲”视为获得持续控制权。
原厂公开驱动参考源码退出循环会stopStreaming，但在用定制二进制退出路径尚未实机验证。

交接须先统一管理程序的启动/重启权、充电休眠请求和新节点的生命周期，再退出原厂节点，
确认控制连接与UDP端口释放后授予新驱动权限。配置或启用失败应撤销新驱动、恢复原厂启动权，
重新验证原厂扫描恢复。整个交接期间导航应撤销就绪，不能容许无雷达数据时继续运行。
claim()只是对上层所有权结果的契约入口，不是实际互斥机制；尚未实现生产交接监督程序，
不能通过调用claim伪装成已排除原厂。这一阶段没有修改/重启原厂管理程序或驱动。

## 最新采集与发布架构（2026-11-08）

`managed_node.cpp` 的 UDP 接收/组帧由独立线程持续完成，ROS线程通过短互斥取得最新不可变完整帧。
DDS 发布、节点发现及生命周期回调不会直接阻塞 UDP 队列的消费；中间扫描可合并，原始源时间戳不重写。
生命周期核心和设备TCP控制仍只有一个调用线程；停止/清理先停止并join采集线程，再释放UDP资源。
保留源时钟检查、200ms采集时效与300ms失联检测；真实断流仍进入故障，不能自动恢复运动。
更新后隔离生命周期/TCP/真实录制UDP测试通过，完整实机静止验证见 `native_joint/42992`。
