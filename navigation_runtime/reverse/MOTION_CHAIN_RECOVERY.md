# 运动执行链恢复与验证

本文件记录离线原指令验证结果，不是生产部署或实车验收。

## 已串通的MCU链路

原固件中的完整链路是：

```
0x0800d170 目标接受/历史目标渐变
  -> 0x0800d414 局部互锁、差速换算与第三参数计算
    -> 0x0800b0e8 / 0x0800ab00 保存状态、轮目标符号处理
      -> 0x0800ab84 构造目标帧
        -> 0x08005bfc 最终外设发送边界
```

verify_sub_motion_chain.py直接执行这条原Thumb链，包含原软件浮点函数和实际模式/门控读取函数，仅截获最后一个发送函数。1500组输入下，目标状态、历史值、电机状态、方向标志、帧顺序、帧ID和载荷与恢复模型一致。它比各函数分别打桩的验证多覆盖了调用衔接，但仍不模拟CAN硬件和中断并发。

### 目标接受

0x0800d170读取浮点RAM 0x200000e4。有限输入下，当其严格大于double常量0.3且小于1.5，并且目标线速度参数为正时，函数直接返回。浮点0.3f实际略大于0.3，因此边界不能改成随意的近似比较。

该值由0x08009c70对三路交错数据分别求10点平均后写入，对应第一路；还会进入状态回复。它的物理传感器、量纲、线路用途尚未证明，不能把该阈值称为“30cm障碍物”。

0x08006300最终读取0x20001ea4+1。值为1时，历史线目标超出±80则每次向零移动50，否则归零；历史角目标超出±50则每次向零移动50，否则归零。随后以参数65535调用下一层。其余值保存请求目标，使用调用者参数。对应2340组差分测试通过。

### 差速换算和局部门控

0x0800d414使用目标结构0x20001e68，关键字段：

| 偏移 | 原指令访问类型 | 用途 |
|---|---|---|
| +0 | uint16 | 局部活动标志 |
| +2 | int16 | 线目标 |
| +4 | int16 | 角目标 |
| +7 | uint8 | 换算分母参数 |
| +8 | uint32 | 第三个输出参数的比例 |
| +12 | uint16 | 角目标乘数 |
| +14 | uint8 | 换算比例参数 |
| +16 | int16 | 活动倒计数 |

令V为+2、W为+4、D为+7、B为+12、R为+14：

```
scale = R * 60000 / (D * 3.1415926)
turn = double(float(W) * float(B)) / 2000
A = int16(trunc(((V - turn) / 1000) * scale))
Btarget = int16(trunc(((V + turn) / 1000) * scale))
```

这里保留原厂混合float/double运算及整数截断，未擅自将参数命名为实测轮径、轴距或减速比。第三个输出参数还依赖输入arg、+8及当前是否纯旋转；完整公式见sub_kinematics.c。

当全局模式为2、局部标志原值为1时，函数处理倒计数。线目标为正、角目标为零且三路值任一路小于30/20/30时，清标志/计数并提交零目标。注意这一检查位于倒计数操作之后，不能凭“标志刚被清掉”推断后续分支被跳过。其他路径仍计算轮目标。4000组原软浮点运算及分支测试通过。

## Linux驱动：平滑结果实际怎样进入串口

恢复的driver_frame.c与getdatafromdriver完整正常返回路径比较了2400组，捕获串口写入、注入读结果，比较全部40字节及整个驱动对象状态。

**修正上一阶段的概括：smooth_pwm_auto确实计算两轴，但发送函数只取其返回低16位线速度。角速度从对象+0x724直接读取并限幅，平滑函数返回的高16位未被采用。** 这一点通过注入不同高16位结果验证，不能把“函数计算双轴”说成“实际发送双轴都平滑”。

普通运动帧头为7f 7f 28 02，尾为0d 0a；byte37为byte0..36累加和的负值。byte10..11为平滑后的线目标（限-600..1500）；byte12..13为角目标（限-1000..1000），均大端16位。原调用平滑器dt cap约0.05秒、range=400。数值单位需与上层缩放一起解释。

内部动作字段变化时，函数改发动作字段，该帧速度字节保持零；动作变化并不走平滑调用。模式、动作参数和一次性字段也在同一40字节帧，不能只拦截速度两项就声称拥有完整运动控制权。其余字段的准确映射保存在driver_frame.c，包含原厂分散存放的32位字段，未自行“整理”为不同协议。

0x40d03/0x4159e还存在重复纯旋转命令随机缩放：满足imu_compensate等条件时，角速度乘以0.7+0.03*(rand()%11)。该行为经过汇编核对；没有证明过去某次实车停顿就是它导致。

## DWA的附加PID

linePID_control和dirPID_control不是上游标准DWA仅靠采样评分的逻辑。恢复的dwa_pid.c对应0x317e0/0x31bc0，5000组有限输入（含积分启用、饱和和速度阈值边界）状态和返回浮点位模式完全一致。

它以内部ActualSpeed为历史输出，在其上增加P/I/D项；误差小于与配置速度有关的0.3/0.35/0.7阈值时才启用积分项，并按上下限和误差方向决定是否累加。目标为零会清部分历史状态。它没有在此函数内读取轮速反馈，也没有显式dt。后续重构应区分“内部命令平滑”与“实际速度闭环”，并核对上层怎样更新这些字段，不能只从ActualSpeed名字认定实测反馈。

## 启动与时基已进一步核实

audit_mcu_startup.py执行原启动初始化：从0x0800e658向RAM 0x20000000复制276字节，并从0x20000114清零8964字节。原来仅视为候选的任务表确实被装入RAM，周期任务0x0800c1f8初始倒计数10，重复周期100 ticks。

0x0800806c按核心时钟变量/1000配置SysTick，原指令写LOAD=该值-1、VAL=0、CTRL=7。对8/72/168MHz注入时钟变量的执行均符合，说明软件配置意图为1ms tick。尚未实测实际晶振、时钟树和中断延迟。调度使用due标志，阻塞期间可能合并触发，因此不能把19次周期调用换算成保证1.9秒实车停下。

## 验证和使用

CMake将全部纯C模型构建为一个共享库；recovered_models.h提供统一接口。执行：

```
cmake -S navigation_runtime/reverse/recovered -B analysis/recovered_build
cmake --build analysis/recovered_build -j 2
sh navigation_runtime/reverse/verify_all.sh /tmp/feedbot_reverse_venv/bin/python
```

该库没有串口、CAN、网络或ROS运行节点，不可直接刷写。差分用例和输入边界都在verify_*.py，不能把这些有限测试当成形式化全输入等价证明。
